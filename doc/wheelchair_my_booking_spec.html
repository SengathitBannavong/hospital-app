📋 Wheelchair booking — GET /api/asset/my_booking

Area: Backend (Go)  Effort: S (~half day)  Unblocks: cross-device booking + deletes a fragile FE heuristic

Companion to context/asset_wheelchair_backend_gap.md. Two parts below: Part 1 is for humans; Part 2 is a machine-readable spec for an AI coding agent.

Part 1 — Human-readable spec

Why this endpoint

The mobile app needs to answer one question: "which wheelchair does the current user currently hold?" Today there is no endpoint for it, and assets carry no owner field, and track_asset/asset_health are not ownership-gated (they return 1000 for any asset). So the app cannot tell the user's in-use chair from another user's.

As a workaround the app currently guesses: it diffs find_wheelchairs (which lists only available assets) against an inferred WL-### catalog and confirms in_use via asset_health. This is fragile (assumes contiguous, zero-padded ids) and ambiguous with multiple concurrent users (it has to ask the user "which one is yours?"). The backend already knows the answer — it just doesn't expose it.

The release handler already calls FindActiveBookingByUser(userID) and enforces ownership (ErrDeviceOwnership when the asset doesn't match). This endpoint exposes that same lookup as a read. It is the single highest-leverage fix for the asset module.

Contract

MethodGET
Path/api/asset/my_booking
AuthAuthorization: Bearer <token> (patient). User id comes from the token — no request params.
Request body / querynone

Success — user HAS an active booking

{
  "code": 1000,
  "message": "OK",
  "data": {
    "booking_id": 2,
    "asset_id": "WL-001",
    "device_id": 1,
    "status": "in_use",
    "borrowed_at": "2026-06-14T08:30:00Z",
    "station_id": null,
    "station_name": null
  }
}

Success — user has NO active booking

Return data: null with code 1000 (an empty booking is not an error):

{ "code": 1000, "message": "OK", "data": null }

Errors

  • Auth failures go through the normal middleware (401 / token codes).
  • Do not use SuccessWithCode for any genuine error — it hardcodes message:"OK", which is exactly the bug the app has to work around elsewhere (book's 1010, release's 4004). Return a descriptive message.

Implementation sketch (Go)

  1. Reuse repo.FindActiveBookingByUser(userID) (repository/device_repo.go:170) — it already Preload("Device") and filters status = in_use.
  2. If it returns nil (no record), respond response.Success(c, nil).
  3. Else map DeviceBooking → the DTO above and response.Success(c, dto).
  4. Add a handler method in handler/device_handler.go and register GET /api/asset/my_booking in the router (same Bearer-auth group as the other asset routes).

Acceptance criteria

  • Returns exactly the authenticated user's active (in_use) booking.
  • Returns code 1000, data:null when the user holds nothing.
  • User isolation: never returns another user's booking.
  • No params required; identity strictly from the token.
  • Does not emit message:"OK" on any real error path.

What the frontend will do once this ships

  • Replace AssetRepository.discoverInUseAssets() (the WL-### heuristic) with a single GET my_booking call.
  • ActiveBookingNotifier.recover() / page-entry simply adopts data.asset_id, or clears when null — delete the "pick which is yours" dialog.
  • Ownership becomes certain and correct across phones/reinstalls.

Related backend fixes (same module, file together)

  1. release_asset: accept the numeric station_id PK (keep station_name as fallback). FE currently sends the renameable station_name as a workaround.
  2. Stop using SuccessWithCode for errors across device handlers — return descriptive messages (fixes book 1010 / release 4004 showing "OK").
  3. Add poi_id / coordinates to asset_stations rows → enables release-at-nearest-station / by user position.
  4. (Optional) Make track_asset ownership-gated (return 1009 for assets the caller doesn't hold), so the FE's existing 1009 track handling becomes meaningful.
